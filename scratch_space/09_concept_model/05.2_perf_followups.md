The first **successful** real run of the phase-5 pipeline (after the 5.1 fixes)
went end to end by hand for `en` + `pt`: `01_download` and `02_transform` both
completed, and the `explore` notebook connected to the resulting store. Outputs
are still in the notebooks. No crashes - the 5.1 blockers (str `ili`, collection
download, ambiguous `it`, kaikki OOM) are all resolved. Three non-blocking issues
remain, recorded here for a later pass; none of them stop the build shipping.

Observations 2 and 3 (store load latency, memory) are acted on in

*measure-and-fix*.

## Observation 1 - considerable slug collisions

`02_transform` produced a **considerable** number of concept-slug collisions.
This is expected to some degree (the `c__{slug}__{hash[:12]}` id keeps concepts
unique via the hash even when slugs match), so it is a *legibility* problem, not a
correctness one - many ids share the same human-readable `{slug}` and only differ
by hash. Root cause is `_pick_slug_source` falling back to the same English lemma
(or `"concept"`) for many distinct synsets.

Follow-up (defer to phase 8 - LLM maintenance already lists "slug dedup"):
- Quantify: how many slugs are shared, and by how many concepts each.
- Decide whether to disambiguate slugs at ingestion (e.g. append POS or a
  distinguishing lemma) or leave it to the phase-8 dedup pass. The hash already
  guarantees id uniqueness, so this is purely about readability.

## Observation 2 - `explore` store load takes > 5 minutes

Connecting the `explore` notebook to the final (full en/pt) store took **over
five minutes** to load. Suspected cause: a `get_all_concepts()`-style eager full
scan reconstructing every model through the codec, which is not a smart thing to
do for the whole corpus (it was fine at sample scale).

Follow-up:
- Profile the load path; confirm whether `get_all_*` / full-table reconstruction
  is the cost.
- Consider caching the built SQLite DB (build once, reuse) and/or making the
  notebook do bounded point/filter queries instead of `get_all_*`.
- Likely a store-layer concern (phase 4.x), not ingestion. Cross-reference Bug D's
  "next memory ceiling" note in `05.1_ingestion_fixes.md`.

## Observation 3 - memory is borderline

Peak memory during the build/load was **borderline** on this (modest) machine. It
completed for `en` + `pt`, but the full five-language build will likely strain it -
exactly the "OMW backbone is the next memory ceiling" note flagged under Bug D in
`05.1_ingestion_fixes.md`.

Follow-up:
- Measure actual peak RSS for the en/pt build and the store load separately.
- Revisit the deferred restructure (write per-language, do not hold all five
  languages' models at once; ILI-keyed merge across per-language passes) before
  attempting the full five-language build.

## Not blocking

The build works and produces a loadable store. These are quality/perf items, not
correctness defects. The committed sample slice and the full five-language build
can proceed once Observations 2-3 are understood enough to not wedge a small box.
