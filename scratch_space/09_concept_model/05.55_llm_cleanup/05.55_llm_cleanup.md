## Principle

Deterministic first, LLM last, review before meaning changes. Ids are rebuilt, not
patched: a slug change rewrites `c__{slug}__{hash}` everywhere it is referenced
(senses, relations, sample), so slugs are fixed **in the pipeline and rebuilt**, never
edited into the Parquet post hoc. Gloss edits do not touch ids and flow through the
validated `export_table` -> review -> `import_table` round-trip.

## Work item A - slug legibility (mechanical, auto-apply)

Goal: a human scanning ids should usually be able to tell concepts apart without reading
the hash. Ids stay unique regardless (`hash[:12]`); this is legibility only.

Tiered slug construction in `sources/omw.py` (replacing the current single-source
`_pick_slug_source` fallback chain):

1. **Tier 0 (as today):** slug from the preferred lemma / OMW-ILI key. If unique among
   the build's concepts, keep it.
2. **Tier 1 (deterministic):** for colliding groups, append the lexfile discriminant
   (e.g. `c__cut-noun-act__...` vs `c__cut-verb-contact__...`; drop the redundant
   `noun./verb.` prefix when the slug's POS is obvious). Resolves ~half the collisions.
3. **Tier 2 (LLM, propose-for-review then baked in) - DEFERRED to phase 8 (Q1,
   2026-07-11):** for the ~9,782 groups colliding within one lexfile, an LLM picks a
   1-3 word qualifier **extracted from the English gloss** (e.g. `c__aaron-baseball__...`
   vs `c__aaron-high-priest__...`), constrained to gloss words so it cannot hallucinate
   meaning. Output is a reviewable `(concept grouping key -> qualifier)` table; after
   review it becomes a **committed input to the build** (Q2 decided: small JSONL in
   normal git, like the seed - a curated input, not a patch layer), so rebuilds are
   deterministic and idempotent. This phase ships tiers 0-1 only; tier 2 is phase 8's
   first real LLM job, with the table-as-committed-input decision already made.
4. **Tier 3 (fallback):** any group still colliding after tier 1 keeps the tier-1 slug;
   the hash already guarantees uniqueness. No `concept` generic slugs should survive
   tier 1 (currently 1).

Consequences of re-slugging (all handled inside the rebuild):

- concept ids change globally -> senses / concept_relations / sample slice all
  regenerate in the same build; the persisted `_store.sqlite` cache re-keys via its
  content signature automatically.
- `lang-tutor` is untouched (it consumes lemmas only; lemma ids do not change).
- the 05.4 gate re-run validates referential integrity after the id churn - this is
  exactly what the invariants are for.

## Work item B - `definition == lemma` repair (semantic, propose-for-review)

First **classify** the 20 rows - the samples show two distinct kinds:

- **Benign coincidence** (majority): the gloss is a legitimate short definition that is
  *also* a member form of the same synset ("capital of Louisiana" is both Baton Rouge's
  gloss and a member lemma; "pour out" both glosses and belongs to the `decant` synset).
  The information content is low but not wrong.
- **Genuinely thin gloss**: the gloss restates the lemma itself with nothing added
  (`c__dear__` glossed "earnest", it-language `far sapere` glossed "far sapere").

Then repair: an LLM chain drafts a fuller English (or Italian, for the 3 it rows) gloss
grounded in the synset's members, hypernym concept, and lexfile - flag, never silently
overwrite. Proposals land in a reviewable JSONL; accepted rows apply via
`export_table` -> edit -> `import_table` (rows re-tag `source=llm` per the provenance
seam). At 20 rows this is minutes of review; the value is exercising the phase-8 loop
shape end to end, not the 20 rows themselves.

**Q3 decided (2026-07-11): re-scope the check.** Benign coincidences (gloss equals a
*different* member of a multi-member synset) are accepted as valid OMW glosses and stay
untouched; the `definition == lemma` query in `lang_tools.lexicon.quality` is re-scoped
to count only glosses that equal the *sole* matching member (genuinely thin), so the
invariant converges to 0 instead of carrying a permanent accepted residue. The LLM
repair then targets only the genuinely-thin remainder (expected single digits).
`DEFINITION_EQUALS_LEMMA_BASELINE` is re-measured under the new scope in the same change.

## Machinery

- **Slug tiers 0-1** live in `sources/omw.py` (pure, unit-tested). No LLM in this
  phase's slug work (Q1); the tier-2 qualifier chain is specified but built in phase 8.
- **LLM chains** follow the existing `src/lang_tools/llm/` pattern (thin
  `StructuredLLMChain` wrappers): this phase builds only the **gloss-repair chain**
  (~20 rows, cost negligible - see Q5), with a pure prompt-building core that is
  unit-testable without calls. Phase 8's tier-2 qualifier job should run through the
  **Batch API** (-50%, non-latency-sensitive; sized in Q5 at < $10 even on Opus).
- **Proposal artifacts** are JSONL under the raw/staging area (gitignored except the
  reviewed slug-qualifier table, which is a committed build input); a thin notebook under
  `notebooks/lexicon_maintain/` drives propose -> review -> apply, logic in the package.
- **Autonomy per the Step 5 rule:** auto-apply mechanical tier-1 slugs; propose-for-review
  for tier-2 qualifiers and every gloss change.
- **Gate:** full rebuild + re-run the 05.4 quality notebook; invariants must hold and the
  slug-collision totals / `definition == lemma` counts drop as predicted. Update
  `DEFINITION_EQUALS_LEMMA_BASELINE` only if the check itself is re-scoped (Q3).

## Run note - the 2026-09-01 gloss repair

The one-row propose -> review -> apply run, recorded because it deviates from the
machinery this phase built.

**The chain did not run.** `~/cred/lang-tools/.env` still has no `OPENAI_API_KEY`, and
the decision was to skip the LLM call rather than move a key between cred files. The
reviewer authored `proposed_definition` directly and the proposal went through the real
`GlossProposal` -> JSONL -> review -> `apply_gloss_proposals` -> gate path. So the loop's
review/apply/gate half is exercised on the real corpus; `gloss_repair.py` and
`prompts/gloss_repair/v1.jinja` remain **tested but never called against a live model** -
phase 8 is their first real exercise.

**The review question (member or gloss?).** The handoff flagged that it `attenzione` on
`c__mind-noun-cognition__93923c10626c` (en gloss "attention", sole en member "mind") might
be a translation artifact, i.e. that the *member* rather than the gloss was the defect.
It is not. The concept is Princeton's {mind} "attention" sense, example "don't pay him any
mind", hypernym {notice, observation, observance}; Italian "attenzione" carries that
heed/notice sense too, and OMW already lists it on the three genuine `attention` synsets
and on `caution` / `kindness`. The member stays; the gloss - a bare echo of the member -
was the defect.

Applied gloss (it):
`considerazione o riguardo che si dà a qualcuno o a qualcosa, notandolo e tenendone conto`

**Result.** Exactly one concepts row rewritten (verified by full-row anti-join against a
pre-apply copy: same row count, same schema, en gloss and examples untouched), provenance
`omw` -> `llm` on that row only, so the concepts table is now 117,658 `omw` + 1 `llm`. All
four invariants pass with the baseline at 0; `report.md` regenerated.

**Side finding, routed to phase 8 (not acted on here).** Reviewing this concept's members
surfaced a POS-attachment defect in the en and fr wordnets: fr `esprit` is attached to all
22 concepts whose English member is "mind" or "spirit", verb synsets included
(`c__mind-verb-cognition__`, `c__spirit-verb-change__`, `c__beware__`), where it is not a
translation of the sense. Measured as noun-tagged lemmas sitting on `verb.*` concepts:
fr 7.84% and en 5.63% of senses, against it 0.53% / pt 0.39% / es 0.33%. The en figure
says part of this is the model storing one POS per lemma form rather than a French-only
import bug, so the number is a smell, not a verdict - it needs its own diagnosis before
any cleanup.
