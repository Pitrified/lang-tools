# Phase 5.1 - ingestion fixes (first real OMW/kaikki run)

The first real run of the phase-5 notebooks (`01_download` + `02_transform` for
`en`/`pt`) surfaced three concrete defects in the OMW path. Two are blockers (the
transform crashes; the download grabs every language), one is a correctness trap
for `it`. Full execution log in
[`05_ingestion/00-first-time.md`](05_ingestion/00-first-time.md). This sub-plan
is the analysis + the fix; it is **md-only** for now (no code edits yet).

All three live in `src/lang_tools/lexicon/ingestion/`; none touch the codec, the
store, the models, or the provenance design - those held up. The mistakes are all
in the thin `wn` adapter (`sources/omw.py`) and `acquire.download_omw`, exactly
the layer I flagged as untested against real `wn`.

Environment that reproduced everything: `wn` 1.1.0, OMW 1.4, raw cache at
`data/_raw/lexicon/wn_data` (already populated by the run).

## Bug A (blocker) - `synset.ili` is a `str`, not an object

### Symptom

`02_transform` dies immediately in `wn_synset_entries`:

```text
File ".../ingestion/sources/omw.py", line 206, in wn_synset_entries
  ili=ili.id if ili is not None else None,
AttributeError: 'str' object has no attribute 'id'
```

### Cause

I assumed `wn`'s `Synset.ili` returns an ILI object exposing `.id`. In `wn`
1.1.0 it returns the **interlingual-index id as a plain string** (e.g.
`'i35545'`) or a falsy value when the synset has no ILI. Verified directly:

```text
ili types over 3000 en synsets: Counter({'str': 3000})
sample: ['i35545', 'i35546', 'i35547']
```

So `ili.id` is wrong; the string *is* the id.

### Fix

In `wn_synset_entries`, stop reaching for `.id`. Be tolerant of both shapes
(future `wn` could return an object) and normalize the empty case:

```python
raw_ili = synset.ili
ili_id = getattr(raw_ili, "id", raw_ili) or None   # str -> itself; obj -> .id; falsy -> None
...
SynsetEntry(..., ili=ili_id, ...)
```

`group_to_records` already treats a falsy `ili` as "monolingual, group by synset
id", so `None` here is the correct signal and needs no change downstream.

### Test to add

The pure layer is already covered. Add one tiny guard so the regression is caught
without a download: refactor the `raw_ili -> ili_id` line into a module-level
`_ili_id(synset)` helper and feed it a fake synset whose `.ili` is a bare string
(and one whose `.ili` is `""`/`None`). No `wn` needed.

## Bug B (blocker) - the OMW download ignores the language filter

### Symptom

`download_omw(['en', 'pt'], ...)` downloaded the **entire** OMW 1.4 collection -
~30 lexicons (da, es, iwn, nn, he, arb, ja, gl, ro, fi, ...) - and the manifest's
`lexicons` listed all of them, not `en`/`pt`:

```text
Downloading OMW omw:1.4 for ['en', 'pt']
Added omw-da:1.4 (DanNet) ... Added omw-ja:1.4 ... Added omw-fr:1.4 ... (30+ lexicons)
```

### Cause

`download_omw` calls `wn.download("omw:1.4")`, which is the **collection**
specifier - it pulls every member lexicon regardless of `langs`. `langs` was only
used for logging and was never turned into per-lexicon download targets. The
`lexicons` field was then built from `wn.lexicons()` (everything installed), so
the manifest over-reported too.

### Fix

Download per-lexicon, driven by an explicit `lang -> OMW lexicon specifier` map
for the five target languages, and record only those in the manifest:

```python
#: ISO 639-1 -> OMW 1.4 lexicon specifier. OMW lexicon ids are not always
#: `omw-{iso}` (and `it` has two wordnets - see Bug C), so map explicitly.
OMW_LEXICONS: dict[str, str] = {
    "en": "omw-en:1.4",
    "pt": "omw-pt:1.4",
    "es": "omw-es:1.4",
    "fr": "omw-fr:1.4",
    "it": "omw-it:1.4",   # MultiWordNet; not omw-iwn (ItalWordNet)
}

def download_omw(langs, *, data_fol, omw_version="1.4"):
    wn = _require_wn(); ...set data dir...
    specs = [_omw_lexicon(lang, omw_version) for lang in langs]   # raises on unknown lang
    for spec in specs:
        wn.download(spec)          # idempotent: wn skips an installed lexicon
    return {
        "wn_version": wn.__version__,
        "omw_version": omw_version,
        "languages": list(langs),
        "lexicons": specs,         # only what we asked for
        "wn_data_dir": str(wn_data),
    }
```

Add an `UnknownOmwLanguageError` (mirroring `UnknownKaikkiLanguageError`) for a
language with no mapping, so an unsupported code fails loudly at acquire time
rather than silently downloading nothing.

Notes:
- Verify `wn.download("omw-en:1.4")` accepts a single-lexicon specifier (the
  collection form worked; the per-lexicon form is the documented granular path).
  If a build wants the whole collection, that is now an explicit choice, not the
  default.
- The already-downloaded full collection on this machine is harmless and makes
  re-runs free (wn skips installed lexicons); the fix matters for a clean machine
  and for an honest manifest.

## Bug C (correctness) - `wn.Wordnet(lang=...)` is ambiguous for `it`

### Symptom / cause

`wn_synset_entries` builds `wn.Wordnet(lang=language)`. For `it` that matches
**two** installed lexicons and silently merges them, with a warning:

```text
WnWarning: multiple lexicons match lang='it': ('omw-iwn:1.4', 'omw-it:1.4');
use the lexicon parameter instead to avoid this warning
lang='it' synsets (both lexicons): 50564
omw-it only synsets:             35001
```

Merging two Italian wordnets duplicates the Italian synset stream and makes the
build non-deterministic w.r.t. which lexicons happen to be installed - directly
against the "deterministic, reconstructible baseline" guarantee phase 5 rests on.
`en`/`pt` happened to be unambiguous, which is why the run got past this to Bug A.

### Fix

Drive the reader from the **same** `OMW_LEXICONS` map and select by lexicon, not
language:

```python
def wn_synset_entries(langs, *, data_dir=None, omw_version="1.4"):
    wn = _require_wn(); ...set data dir...
    for language in langs:
        spec = _omw_lexicon(language, omw_version)      # explicit, single lexicon
        wordnet = wn.Wordnet(lexicon=spec)
        for synset in wordnet.synsets():
            ...
```

This removes the warning, pins each language to exactly one wordnet, and makes the
synset stream reproducible. `SynsetEntry.language` stays the ISO code we passed in
(the lexicon is an implementation detail of *which* wordnet supplied it).

## Bug D (blocker) - kaikki is loaded fully into memory, not streamed (OOM)

### Symptom

Running `02_transform` crashed the machine with memory exhaustion. The kaikki
dumps are hundreds of MB of JSONL per language (millions of entries); the whole
lot is held resident at once.

### Cause

`load_kaikki_entries` *is* a generator - good - but its laziness is thrown away
twice downstream:

1. `pipeline.load_sources` does `kaikki_entries.extend(load_kaikki_entries(...))`
   for every language, **materializing every entry of every dump into one list**
   ([`pipeline.py`](../../src/lang_tools/lexicon/ingestion/pipeline.py), `load_sources`).
2. `transform` then builds an `enrichment` dict over that whole iterable, keeping a
   `KaikkiEntry` (with its gloss list + example objects) for **every kaikki
   headword**, the vast majority of which never join onto an OMW lemma.

So peak memory is the full kaikki dump x5 languages, on top of the OMW backbone -
the latter alone is the ~1.9 GB-resident graph the phase-3 analysis measured. The
kaikki list is the part that tips it over.

### Fix - filter against the backbone while streaming

The enrichment only ever joins onto an OMW lemma, so the set of keys we can
possibly use is exactly the OMW lemma keys - a *bounded* set (~hundreds of k),
independent of the kaikki dump size. Build the backbone first, derive the needed
keys, then stream each dump line-by-line keeping **only** matching entries and
discarding the rest immediately.

`transform` already groups OMW before reading kaikki, so the order is right; it
just needs to (a) compute the needed-key set and (b) take kaikki as a lazy stream:

```python
def transform(omw_entries, kaikki_entries=()):
    concepts, lemmas, senses = group_to_records(omw_entries)

    needed = {(lem.normalized, lem.language) for lem in lemmas}   # bounded by OMW
    enrichment: dict[tuple[str, str], KaikkiEntry] = {}
    for entry in kaikki_entries:                 # streamed, never listed
        key = entry.key
        if key in needed and key not in enrichment:
            enrichment[key] = entry              # cap = |needed|, not |kaikki|
    ...
```

The only hard requirement is that `kaikki_entries` reaches `transform` as a lazy
iterator. So `pipeline` must stop building the list:

```python
import itertools

def load_sources(langs, *, data_fol):
    langs = list(langs)
    omw_entries = list(wn_synset_entries(langs, data_dir=...))   # backbone, bounded by OMW
    kaikki_streams = []
    for language in langs:
        path = kaikki_path(data_fol, language)
        if path.exists():
            kaikki_streams.append(load_kaikki_entries(path, language))
        else:
            lg.warning("No cached kaikki dump for {} at {}", language, path)
    return omw_entries, itertools.chain.from_iterable(kaikki_streams)   # lazy
```

`build_initial` passes that straight through, so the file handles open and close
one at a time and only matched entries are retained. `load_kaikki_entries` already
reads the file with a `with` block and yields per line, so no change is needed
there - it was always streamable; the callers just have to honour it.

### Caveat / interaction with `build_initial`

`build_initial` currently has a single `if omw_entries is None or kaikki_entries is
None:` branch that pulls both from `load_sources`. Keep `kaikki_entries=None` as
"stream from cache" and only call `list()` on the OMW side. Do **not** add a
`len()`/truthiness check on the kaikki stream (it would consume the generator);
the empty-dump case is already handled by `enrichment` simply staying small.

### Test to add

Feed `transform` a deliberately one-shot iterator (e.g. `iter([...])`) of kaikki
entries where most keys are absent from the OMW backbone, and assert (a) the
non-matching entries are dropped and (b) the iterator is consumed exactly once
(wrap it in a generator that counts yields). No large data needed - this pins the
"streamed, filtered, single-pass" contract.

### Note - OMW backbone is the *next* memory ceiling

Streaming kaikki removes the dump-sized spike, but the OMW backbone held as
`SynsetEntry` plus the produced pydantic models is still the ~1.9 GB-resident graph
from phase 3. `en`/`pt` fit; the full five-language build may still strain a small
box. If it does, the follow-up is to **write per-language and not hold all five
languages' models at once** (group_to_records would need an ILI-keyed merge across
per-language passes, or a two-pass build) - a larger restructure tracked
separately, not part of 5.1. `SynsetEntry` being a frozen dataclass of plain
strings (not pydantic) already keeps the OMW-read side as cheap as it can be.

## Shared piece: one `lang -> lexicon` map, one helper

Bugs B and C share a root cause: the language was never resolved to a concrete OMW
lexicon. Fix once:

- Put `OMW_LEXICONS` + `_omw_lexicon(lang, version) -> spec` (raising
  `UnknownOmwLanguageError`) in `sources/omw.py` (it already owns the OMW domain),
  and import it into `acquire.download_omw`. Keep the `:1.4` version a parameter so
  a future OMW bump is a one-liner.
- `acquire.download_omw` and `sources.wn_synset_entries` both go through it, so the
  download set and the read set can never drift.
