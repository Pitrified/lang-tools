# Phase 5.56 - rebuild and gate: materialize the clean corpus, then prove it

Steps 6 and 7 of [`05.5_cleanup.md`](../05.5_cleanup.md) are written as separate steps but
share one prerequisite: a freshly rebuilt corpus.
Step 4's first slice changed the pipeline (kaikki gone, CILI fallback, `lexfile` / `examples`
/ hypernym edges added, `CACHE_VERSION` -> 2), but the **five-language corpus on disk was last
built on 2026-06-18, before any of that**.
The current [`05.4_data_quality/report.md`](../05.4_data_quality/report.md) still describes a
kaikki-tagged corpus (62,612 kaikki concepts, 7,220 `definition == lemma` rows, kaikki examples).
Nothing downstream can be trusted until the corpus is rebuilt from the re-cut pipeline and
re-measured.

This sub-plan does exactly that and nothing more: rebuild, gate, snapshot licensing.
It does **not** do the Step 5 LLM cleanup - that needs the rebuilt corpus's *actual* residue in
front of it, which is the whole point of running this first.

## Principle

Materialize, then measure.
Step 4 was verified by unit tests on synthetic rows; this phase verifies the **real build** of
all five lexicons produces a corpus that satisfies the invariants the cleanup promised.
The 05.4 quality notebook was a one-off read-only diagnosis with inline SQL and hand-written
prose; here its checks move **into the package** as a clean, tested module and the notebook
becomes a thin caller that regenerates the report on every run, so "quality is measured each
time, not assumed" ([`05.5_cleanup.md`](../05.5_cleanup.md) Step 6) - measured by re-running the
notebook, not by a separate test harness on a sliced corpus.

## Why 7 before 6 before 5

- **Step 7 (rebuild) is the prerequisite.** Both the regression checks and the LLM cleanup run
  *over the rebuilt corpus*. Without it they measure stale kaikki data.
- **Step 6 (checks) wraps the rebuild.** The four invariants only mean something against a real
  build, so the extracted check module is wired into the notebook and run here, in the same pass.
- **Step 5 (LLM cleanup) comes after.** It spends a limited LLM budget on the residual
  `definition == lemma`, slug collisions, and orphans - which you can only size once this phase
  reports them from the clean corpus, ranked by the frequency / connectivity signals Step 4 fed in.

## Stage B - extract the checks into the package, run from the notebook (Step 6 body)

The 05.4 diagnosis notebook
[`05.4_data_quality_checks.ipynb`](../05.4_data_quality/) computes every number as an inline
DuckDB query and hand-writes the report prose. That is the thing to fix: the SQL and the
report-rendering move **into the package** as a clean, reusable, tested module, and the notebook
becomes a thin caller. No SQL or report text is ever copy-pasted again.

The shape:

- **A data-quality module in `src/lang_tools/lexicon/`** holds each check as a named function
  (or a registry of named queries) returning a typed result, plus a renderer that writes
  `report.md` from those results. The queries are the single source of truth; the module is
  unit-testable on its own (the SQL parses, the renderer formats), without needing a corpus.
- **The notebook only wires it**: open the rebuilt corpus, call the checks, write the report.
  Same pattern as the 5.54 staging / topic notebooks (thin caller, loguru, findings cell).
- **The report is generated, never authored.** Re-running the notebook against any corpus
  regenerates [`05.4_data_quality/report.md`](../05.4_data_quality/) wholesale. The prose that is
  interpretation (not numbers) lives in the renderer as templated text keyed off the results, so
  there is no drift between the numbers and the words describing them.

**No automated test on a sliced corpus.** A pytest gate that builds or slices a fixture corpus
adds more complexity than it buys (how do we slice it, keep it referentially closed, keep it
deterministic) for a build that already has the standing writer-level guard
`test_no_row_is_tagged_kaikki`. The regression check is **running the notebook**; the unit tests
cover the query module's mechanics, not a synthetic corpus.

The four invariants the notebook reports (and reads as the pass/fail signal) on the rebuilt
corpus:

| invariant | 2026-06-18 (kaikki) value | required after rebuild |
| --- | --- | --- |
| kaikki-tagged share | 62,612 concepts / 62,364 lemmas | **0** (`test_no_row_is_tagged_kaikki` guards the writer; the report confirms it on disk) |
| `definition == lemma` rows | 7,220 (6,568 concepts) | drops sharply (kaikki's share gone; residual is OMW-internal, sized for Step 5) |
| sense -> missing lemma / concept | 0 | stays 0 |
| lemma with no sense | 0 | stays 0 |

The notebook surfaces these prominently (the report leads with them) so a regression is obvious
on a re-run; the hard-zero invariants are the kaikki share and the two edge-reconciliation
checks, while `definition == lemma` is a "sharply lower than the recorded 7,220 baseline"
reading, not an exact number.

## Findings (executed 2026-07-11)

**Stage A - rebuild.** `download_omw` reused the cached wn data (CILI included) and the
full en/pt/es/fr/it build ran in ~140 s at 1536 MB peak RSS on this box - no per-language
restructure needed (5.2 Observation 3 stays closed). Counts: 117,659 concepts / 321,126
lemmas / 491,876 senses (same backbone shape as the kaikki build, as expected: kaikki only
annotated) plus **97,666 hypernym `ConceptRelation` edges** (new). Step-4 fields populated:
`lexfile` on all 117,659 concepts (45 distinct), `examples` on 33,396 concepts (en 32,921 +
it 1,435). Provenance is `{omw}` only; the CILI fallback fired 0 times (dormant as
documented). Sample slice re-carved (149 lemmas / 50 concepts / 160 senses).

**Stage B - gate.** Checks + renderer extracted to `src/lang_tools/lexicon/quality.py`
(check registry -> typed `CheckResult`s, four `InvariantResult`s, markdown renderer;
8 unit tests on a tiny synthetic corpus); the 05.4 notebook is now a 3-cell thin caller.
All four invariants **pass** on the rebuilt corpus:

| invariant | value | required |
| --- | --- | --- |
| kaikki-tagged rows (sources list + on-disk source) | 0 | 0 |
| dangling sense / relation endpoints | 0 | 0 |
| lemmas with no sense | 0 | 0 |
| `definition == lemma` rows | **20** | sharply below 7,220 |

The `def==lemma` residue for Step 5 is tiny (20 rows; the 7,200 kaikki-injected ones are
gone). Non-en gloss coverage dropped to real OMW coverage as accepted: en 100%, it 6.1%,
pt/es/fr **0%** (those OMW wordnets ship no definitions at all). Slug collisions persist
(86,384 distinct slugs / 117,659 concepts, ~27%) - still phase 8.

**Stage C - licensing.** Per-lexicon licenses from the `wn` metadata (confirmed against
the OMW 1.4 index):

| lexicon | resource | license |
| --- | --- | --- |
| omw-en | Princeton WordNet 3.0 | WordNet license (permissive, attribution) |
| omw-pt | OpenWN-PT | **CC BY-SA** |
| omw-es | MCR (Spanish) | CC BY 3.0 |
| omw-fr | WOLF | **CeCILL-C** (weak copyleft) |
| omw-it | MultiWordNet | CC BY 3.0 |

So the "no CC-BY-SA anywhere" posture does **not** hold: dropping kaikki removed the
*added* share-alike text, but the Portuguese backbone itself is CC BY-SA as packaged in
OMW 1.4, and WOLF is CeCILL-C. Upstream OpenWordnet-PT has since relicensed to CC-BY 4.0
(github.com/own-pt/openWordnet-PT), so re-sourcing pt from upstream is the clean fix -
that call (re-source vs per-language licensing vs accept SA for pt) is **phase 10's**,
recorded in [`10_licensing_docs.md`](../10_licensing_docs.md).
