# Phase 5.58 - accepted gloss repairs become a committed build input

Closes the gap [`05.57_junk_forms/05.57_junk_forms.md`](../05.57_junk_forms/05.57_junk_forms.md)
found the hard way: its rebuild regenerated `concepts.parquet` from OMW and silently
reverted the 5.55 gloss repair, turning the gate red.
Today a curated gloss survives only until the next `build_initial`.

This is not a new decision, it is an existing one applied to the right object.
5.55's Q2 already settled the shape for the slug-qualifier table: *the reviewed output
becomes a committed input to the build, so rebuilds stay deterministic without re-running
the LLM, and the review effort is preserved.*
Glosses were left out on the reasoning that gloss edits do not feed `concept_id` - true,
and beside the point, because a rebuild regenerates every column regardless.

## Shape

The maintenance loop's output **is** the build's input - same file format, same model, no
second schema:

- Accepted `GlossProposal` rows live in `data/curated/gloss_overrides.jsonl`, committed to
  git. `data/` is gitignored wholesale, so the file is force-added exactly as the
  `data/bootstrap/*.jsonl` seed already is - the existing precedent for a curated input
  under `data/`.
- `build_initial` applies them right after `transform`, before anything is written: each
  override sets `definitions[language]` on its concept and re-tags that row `llm`, the
  same provenance rule `apply_gloss_proposals` uses on the Parquet.
- `apply_gloss_proposals` (the post-hoc Parquet path) stays as it is. It is still the
  right tool for repairing the corpus you have without a 15-second rebuild; the committed
  file is what makes the repair *durable*. The reviewer's workflow gains one step: append
  the accepted proposals to the curated file.

## Stale overrides

An override names a concept id, and ids are rebuilt (a slug change rewrites them). So an
override can outlive its concept.

Decision: **warn and count, do not fail the build.** A hard failure would block every
rebuild after a legitimate re-slug, which is the operation 5.55 explicitly wants to stay
cheap. The count goes into the build summary and the log, and the gate is the backstop -
a dropped repair shows up as `definition == lemma` climbing back above 0, which is exactly
how 5.57 caught this in the first place. Nothing is lost silently: the override stays in
git, it just did not apply.

## Result (2026-09-01)

Rebuilt from scratch with the curated file in place and **no post-hoc apply step**:

```
Applied 1 curated gloss override(s), 0 stale
c__mind-noun-cognition__93923c10626c
  it -> "considerazione o riguardo che si da a qualcuno o a qualcosa, ..."
  source -> llm
definition_equals_lemma 0, all four invariants PASS
```

The same rebuild that silently reverted the repair in 05.57 now reproduces it. Counts are
unchanged from 05.57 (321,082 lemmas / 117,659 concepts / 490,825 senses), provenance is
117,658 `omw` + 1 `llm`, and `_build.json` records the override counts so a build's
curated state is auditable from the manifest alone.

Reviewer workflow, now two steps instead of one: apply the accepted proposals to the
corpus you have (fast, no rebuild), **and** append them to
`data/curated/gloss_overrides.jsonl` so the next rebuild keeps them. The gloss-repair
notebook says so at the review step.
