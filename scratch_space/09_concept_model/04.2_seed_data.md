# Seed data and data loading

Follow-up to [`04.1_sqlite_mode.md`](04.1_sqlite_mode.md). 4.1 left the store with
**two ways to get models off disk** - a Parquet loader and a JSONL-seed loader,
wired as a runtime fallback chain. This file analyses that mess and the
single-loader plan (decisions folded in below).

## The problem (what "double loading" actually is)

The SQLite engine itself is single. The duplication is one level up, in *how
models are loaded before they hit SQLite*. `LexiconStore.from_data_fol` calls
`_load_corpus_models`, which today is:

```python
def _load_corpus_models(data_fol):
    if _parquet_present(data_fol):          # data/lexicon/*.parquet
        try:
            return _load_table(...)         # codec, needs pyarrow (store extra)
        except StoreDependencyMissingError:
            ...warn, fall through...
    return _load_seed_models(data_fol)      # data/bootstrap/*.jsonl, stdlib json
```

So there are **two model-loading code paths** (`_load_table` over Parquet,
`_load_seed_models` over JSONL) plus a fallback that silently degrades from
Parquet to seed when pyarrow is missing. On top of that, `corpus.py`'s
inspect/edit tooling only ever sees Parquet. Net effect:

- two loaders to keep in sync with the codec/model shape;
- "what the store serves" and "what `inspect_table` shows" can diverge (store
  reads the seed; inspect reads Parquet);
- a silent pyarrow-missing fallback that hides a misconfigured environment.

## Why it exists (and why that reason is now weak)

4.1 kept the JSONL path deliberately: `sqlite3` is stdlib, so loading the lemma
surface from the seed needs **no** `store` extra (no pyarrow). The stated goal
was "lang-tutor / a bare install reads lemmas without pyarrow".

The reason is weak because **pyarrow is mandatory in production the moment real
data ships**: the phase-5 corpus is Parquet (the whole phase-3 decision), so any
real deployment must `pip install` pyarrow to load the store at all. The
stdlib-only path therefore buys exactly one thing - serving the *tiny sample*
before phase 5 on a bare install - at the cost of a *permanent* second code path
and a divergence bug surface. That is a bad trade. The "no pyarrow" goal only
ever applied to a pre-phase-5 convenience window.

Confirming evidence in the repo:

- The module-level default store builds eagerly at import:
  `_STORE = LexiconStore.from_data_fol(get_lang_tools_params().paths.data_fol)`
  in [`lemma_store.py`](../../src/lang_tools/lexicon/lemma_store.py). It resolves
  today only because the seed is committed and the fallback catches the missing
  Parquet.
- `render.yaml` builds with a bare `pip install .` (no extras), but it is
  leftover from the repo-bootstrap template and is **not a live constraint** -
  ignore it.
- `lang-tutor`'s in-process content source still imports the *pre-rename*
  `lang_tools.words.word_store` - it is already red until phase 9, and its real
  runtime path is HTTP to the webapp, so its pyarrow footprint is not a live
  constraint here (phase 9 reworks it anyway).

## Plan: one loader, Parquet only

**The store reads Parquet only.** The JSONL seed becomes a committed *dev input*,
not a runtime source; a notebook parquetizes it on demand.

1. **Store is Parquet-only.** `from_data_fol(data_fol)` loads `data/lexicon/`
   Parquet via the codec and nothing else. The target folder is already a
   parameter (`data_fol`), so tests / callers point it wherever they like.
   Missing Parquet raises **`CorpusNotFoundError`** with a short message -
   `"Corpus not found at <path>"` - and nothing more. No mention of the seed or
   the parquetize notebook: a dev reads it as "corpus not built yet"; a prod
   user checks the folder and opens an issue if it is genuinely missing. The
   notebook is a dev tool, not a prod concept, so it stays out of the error.
   Delete `_load_seed_models`, `_parquet_present`, and the fallback branch in
   `_load_corpus_models`. `from_models` stays (tests / ingestion build in
   memory).
2. **Seed stays committed JSONL**, exactly as today
   (`data/bootstrap/*.jsonl`), as the human-editable dev fixture. The generated
   sample Parquet under `data/lexicon/` stays gitignored and uncommitted.
3. **A dedicated parquetize notebook** under `notebooks/` turns the seed into
   `data/lexicon/` Parquet. The functionality already exists -
   `corpus.import_table(name, data/bootstrap/<name>.jsonl, data_fol=...)` reads
   the JSONL, validates each row through the model, and writes the canonical
   Parquet. The notebook is a thin loop over `TABLES` calling `import_table`.
   Verified end-to-end on the real seed (301 lemmas -> `lemmas/<lang>.parquet`,
   4 concepts, 18 senses, the two edge tables; `inspect_table` reads them back).
4. **`explore.ipynb` instantiates a store at a chosen folder**, with a
   commented-out line to swap which folder (sample vs full corpus), plus a note
   that a fresh checkout must run the parquetize notebook first.

Mental model the draft nailed: **the seed is a dev-experience fixture, not a
product.** A library user receives the phase-5 Parquet and is happy. A dev who
wants to poke at the data model edits the small JSONL seed, runs the parquetize
notebook, and sees it flow through the real Parquet -> SQLite path - the *same*
path production uses, so there is no second-class sample codepath that can rot.

## Decisions (resolved)

1. **pyarrow placement.** Promote `pyarrow` to base `dependencies`; keep
   `duckdb` in the extra (it is only used by `inspect_table`, QA-only). Loading
   the store is now a core capability, so its dependency is core. `render.yaml`
   needs no thought - it is template leftover.
2. **Default store lifecycle (the line-141 "leave as is?" question): make it
   lazy.** "Leave the eager `_STORE` as is" does not hold up: Parquet-only +
   missing Parquet means the eager build *raises at import time*, which makes the
   whole package **un-importable** on a fresh checkout - not merely "red", but
   breaking every test at collection and the webapp at boot, before any fixture
   can run. The minimal fix is to build the default store lazily on first
   `get_store()` call and cache it. Behaviour is still "red until phase 5" (a
   query raises `CorpusNotFoundError` when no corpus exists), but importing the
   package, running unrelated tests, and pointing a store at a different folder
   all keep working. This is a tiny change (wrap the module global in a function)
   and is the only thing consistent with both "raise on missing Parquet" and
   "tests point the store at a tmp dir".
3. **Test wiring.** Unit tests keep using `from_models`. The on-disk path is
   tested by pointing `data_fol` at a tmp dir (the existing store parameter),
   parquetizing the committed seed into it via `import_table`, then asserting
   `from_data_fol` reads the Parquet. `test_from_data_fol_loads_the_sample_seed`
   is rewritten this way (seed JSONL -> tmp Parquet -> store). Webapp tests get a
   fixture that builds the sample Parquet into a tmp `data/lexicon/` and the
   lazy store reads it. Keep all tests in sync with the new behaviour and the
   committed sample seed.
4. **`corpus.py` docstring.** Simplify the committed-JSONL carve-out: the seed is
   now unambiguously an input, never a runtime source, so the "JSONL is never
   committed except the seed" wording gets cleaner.
5. **Docs** (`docs/library/lexicon.md`, `frozen_api.md`): drop the "store reads
   the seed directly" / dual-source description; document Parquet-only loading
   plus the parquetize step.

## Options considered

| # | Option | Loaders | pyarrow to load | Fresh-checkout store | Verdict |
|---|--------|---------|-----------------|----------------------|---------|
| A | **Parquet-only store + parquetize notebook** (chosen) | 1 (Parquet) | required | raises `CorpusNotFoundError` until parquetized / phase 5 | **chosen** - one path, prod == dev path |
| B | Keep dual-source fallback (status quo) | 2 | optional | works off seed JSONL | rejected - the mess we are removing; silent degrade |
| C | Commit the sample Parquet too | 1 (Parquet) | required | works | rejected by draft + phase-3 "no committed DB/blob"; materialises LFS for a sample, blob not diff-reviewable |
| D | Seed-only store (JSONL always) | 1 (JSONL) | not for sample | works off seed | rejected - full corpus is 400k rows, JSONL ruled out in phase 3 (>100 MB, no LFS delta) |

A is the only option that yields a single loader *and* keeps the phase-3/4.1
storage decisions intact. The cost (pyarrow always required to load) is one we
already pay in production, so we are paying it honestly instead of hiding it
behind a fallback.

## as is

- Two model-loaders in `lemma_store.py` (`_load_table` Parquet via codec +
  `_load_seed_models` JSONL) joined by a pyarrow-missing fallback in
  `_load_corpus_models`; `corpus.py` inspect/edit is Parquet-only.
- `store` extra (pyarrow + duckdb) is optional.
- Default store `_STORE` is built eagerly at import from the real `data/`.
- Seed committed at `data/bootstrap/*.jsonl`; sample Parquet not committed.
