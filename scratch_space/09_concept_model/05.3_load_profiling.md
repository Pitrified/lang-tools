# Phase 5.3 - profiling: store load latency + build memory (full-corpus gate)

## Applied (2026-06-17) - fix done, re-measured

Implemented the streaming load + persistent cache + seed/corpus split (the "Plan
to apply" below). Re-measured on the real en/pt corpus
(`05.3_profiling/profile_after_fix.py` -> `profile_after.log`):

| load | time | peak RSS |
| ---- | ---- | -------- |
| before: real `from_data_fol` | 21.5 s | 1362 MB |
| after, **cold** (stream build + persist) | 16.1 s | **593 MB** |
| after, **warm** (cache hit, bare connect) | **0.001 s** | ~0 |
| `validate=True` (old model path, opt-in) | 23.3 s | 1485 MB |

**The >5 min / OOM is resolved.** First load is ~16 s under ~600 MB (well within
the box now that the double model-materialization is gone and tables stream one at
a time); every subsequent load is a ~1 ms connect to the persisted
`_store.sqlite`. Cold peak dropped ~57% (1362 -> 593 MB).

Note: the warm process's RSS reads higher only because the sanity check then calls
`get_all_concepts()` (117k models, a few hundred MB) - that bulk read, not the
load, is the cost. Confirms `get_all_*` is a smell at full scale; the explore
notebook now points bulk/overview reads at `inspect_table` (DuckDB) instead.

**Five-language go (Observation 3):** with cold peak ~593 MB for en/pt, five
languages projects to ~1.2-1.5 GB cold - feasible on this box without the
per-language-write restructure (5.1 Bug D), and paid only once thanks to the
cache. Re-measure at five languages to confirm; keep the restructure deferred.

What shipped: `codec.load_raw_table` (model-free lean read) + `_table_paths`
helper; store `from_data_fol(validate=False, use_cache=True)` streaming per-table
into a persisted, signature-keyed `_store.sqlite`; `_warn_on_slug_collisions`
summarized to one line; `parquetize_seed.ipynb` now builds `data/bootstrap/lexicon/`
(seed corpus, separate from the real `data/lexicon/`); `explore.ipynb` defaults to
that seed corpus. Tests: raw==validate equivalence, cache persist+reuse, cache
busts on corpus change. `uv run pytest && ruff check . && pyright` green (156).

## Profiling (the investigation)

## Findings (2026-06-17) - profiling done

Profiled the real en/pt corpus under `data/lexicon/` (192,449 lemmas / 117,659
concepts / 272,479 senses) with
`05.3_profiling/profile_load.py` (logs to `05.3_profiling/profile_run.log`).

**The load is memory-bound, not CPU-bound. The ">5 min" was swap thrashing.**
With other apps closed (more free RAM) the full `from_data_fol` completed in
**~21.5 s**, not minutes. The first run **OOM-killed**; the >5 min observation
(05.2) was the box swapping under memory pressure. Phase 3 predicted *seconds* of
CPU - confirmed. The surprise is memory, exactly as the gate suspected.

Clean per-process numbers (fresh interpreter each, `ru_maxrss`):

| path | time | peak RSS |
| ---- | ---- | -------- |
| real `from_data_fol` (`:memory:` db) | 21.5 s | **1362 MB** |
| candidate: parquet rows -> SQLite, no pydantic | 11.9 s | **702 MB** |

Per-table stage costs (frugal, one table at a time):

| table | rows | read | validate | dump | us/row (validate) |
| ----- | ---- | ---- | -------- | ---- | ----------------- |
| lemmas | 192,449 | 3.85 s | 1.80 s | 2.61 s | 9.3 |
| concepts | 117,659 | 1.09 s | 0.55 s | 0.18 s | 4.7 |
| senses | 272,479 | 1.41 s | 1.35 s | 0.94 s | 4.9 |

Bulk reads after load: `get_all_concepts()` 0.83 s, `get_all_lemmas()` 4.16 s.

### Root cause

`from_data_fol` -> `_load_corpus_models` builds **all ~580k pydantic models for
all five tables and holds them in one dict**, then `from_models` -> `_populate`
calls `row_from_model` (a `model_dump`) on every one of them **while they are all
still alive**. So the peak holds: the pyarrow buffers + 580k pydantic objects +
the dumped rows + the SQLite db, simultaneously -> ~1.36 GB for en/pt alone.

pydantic itself is **not** the time sink (validate is ~5-9 us/row, ~3.7 s total);
it is the *retention* of every model that drives the memory peak, and the memory
peak is what makes a small box thrash/OOM. The 05.2 hypothesis (eager
`get_all_concepts`) was **wrong** - the load, not the bulk read, dominates.

### Fix (decided direction): stream lean rows straight into SQLite

Skip the pydantic round-trip on load entirely. The Parquet rows are already in the
exact lean column shape; insert them into SQLite one partition at a time and never
materialize the 580k models. Measured headroom: **11.9 s vs 21.5 s (~1.8x) and
702 MB vs 1362 MB (~½)**. The memory halving is the point - it is what unblocks the
small box and the five-language build.

Two sub-decisions this raises (see "Open decisions" below): whether to keep any
on-load validation, and whether to persist the built SQLite (`db_path`) so the
build is paid once per corpus version instead of every process.

### Memory go/no-go for the five-language build (Observation 3)

en/pt peak is 1362 MB (real) / 702 MB (direct streaming). Five languages is
roughly 2-2.5x this scale, so: real path ~3 GB+ (infeasible on this box), direct
streaming path ~1.5 GB (borderline but plausible). **Provisional: the streaming
fix likely makes the five-language build feasible without the larger
per-language-write restructure** (5.1 Bug D) - re-measure at five languages before
committing either way; keep the restructure deferred unless still over budget.

### Side findings

- **Slug collisions (Observation 1) quantified: 15,740 colliding slug groups** out
  of 117,659 concepts. Confirms "considerable"; routed to phase 8 dedup. Separately,
  `_warn_on_slug_collisions` logs **one warning line per group (~15.7k lines) on
  every load** - real noise and load overhead; it should emit a single summary
  count instead. Small, in-scope cleanup.
- The corpus had **stale tiny seed partitions mixed in** (de/es/fr/it lemmas ~50
  rows each, `senses/_all.parquet` 18 rows) from an earlier parquetize-seed run
  sharing `data/lexicon/`. **Addressed:** the seed now builds its own
  `data/bootstrap/lexicon/` corpus, and `build_initial` clears the corpus dir
  before writing (`_clean_corpus_tables`), so a build is a fresh write. The
  existing stale files self-heal on the next real build (or can be removed by hand
  now - they are seed leftovers, distinct from the real en/pt partitions).

### Open decisions (before applying the fix)

1. **On-load validation**: streaming raw skips per-row pydantic validation (the
   `MalformedRecordError` safety net). For a corpus we produce deterministically
   this is arguably wasted work every load; option to keep an opt-in `validate=`
   flag for paranoia. Recommend: skip by default, since ingestion already validated.
2. **Persist SQLite**: build once to a `db_path` keyed on the `_build.json`
   manifest and reuse, vs rebuild `:memory:` each process. Recommend: persist for
   the full corpus, keep `:memory:` for the tiny sample.

## Plan to apply (decided 2026-06-17)

User decisions: skip on-load validation by default; persist the SQLite keyed on the
corpus; separate the seed corpus from the real corpus.

1. **Streaming load (codec + store).** Add `codec.load_raw_table` (lean rows, no
   pydantic: drops the provenance column, normalizes map columns to dicts) and a
   store `_populate_raw` that inserts those rows straight into SQLite. `from_data_fol`
   uses this by default; pass `validate=True` to take the old model-validating path
   (the `MalformedRecordError` safety net) when wanted. `from_models` (ingestion /
   tests, in-memory models) is unchanged.
2. **Persist SQLite keyed on a corpus signature.** `from_data_fol` builds the DB
   once to `<corpus_dir>/_store.sqlite` and reuses it while a signature (sha256 over
   each parquet file's relpath/size/mtime + a `CACHE_VERSION`) is unchanged; a
   changed corpus busts it and rebuilds. A valid cache hit is a bare
   `sqlite3.connect` - milliseconds, ~0 extra memory. `:memory:`/`use_cache=False`
   stay available for tests and the tiny sample. Signature, not the `_build.json`
   manifest, so the seed corpus (no manifest) caches too.
3. **Seed corpus out of `data/lexicon/`.** The `parquetize_seed` notebook targets
   `data/bootstrap/lexicon/` (co-located with the committed `data/bootstrap/*.jsonl`
   seed; the whole `data/` tree is gitignored, so parquet + `_store.sqlite` stay
   uncommitted). `explore.ipynb` points at the seed corpus by default with a
   commented swap to the real `data/lexicon/`. The real `build_initial` keeps writing
   `data/lexicon/`. `get_store()` default stays the real corpus (no seed fallback -
   honours the phase-4.2 single-load-path decision); tests already build a tmp
   corpus + `set_store`, so they are unaffected.
   - *Flagged consequence:* on a fresh checkout `data/lexicon/` is empty until a real
     build, so manual webapp dev must point at the seed corpus explicitly (the
     conftest pattern) or run a build. Consistent with 4.2; noted so it is a choice,
     not a surprise.
4. **Slug-warning summary.** `_warn_on_slug_collisions` logs **one** summary line
   (`N slug groups collide across M concepts`) instead of ~15.7k lines per load.
5. **Re-measure** the streaming + cache-hit load on the real en/pt corpus and record
   before/after in this file.

## Original plan

This is the **actionable execution** of `05.2_perf_followups.md` Observations 2
and 3. 05.2 is the record of what we saw on the first successful en/pt run; this
sub-plan is the measure-then-decide pass. It is deliberately a *gate*: do not
attempt the full five-language build, commit the sample slice, or move on to
phases 6/7 (which add more rows) until the full-corpus load and memory costs are
understood, because a small box is already borderline.

Scope is **measurement + a decision**, not a big rewrite. Any fix that falls out
(caching, query-shape change) can be small; the per-language-build restructure is
the one larger option, gated on the memory numbers.

## Why this is suspicious (the expectation to test against)

Phase 3 measured the query surface at the OMW five-language scale and predicted
**seconds**, not minutes:

- full graph as pydantic dicts ~1.9 GB resident;
- SQLite point lookup ~30 us; DuckDB raw filter/adjacency scan ~150 ms;
- so reconstructing ~100k concepts at ~30 us each is ~3 s, not 5 min.

The observed **> 5 min** en/pt load is therefore an *anomaly* versus the phase-3
numbers - profiling should find a specific surprise (an N+1 pattern, per-row JSON
re-parse, the senses per-language partition load, or eager hydration), not just
"models are slow". That gap is the whole point of profiling before optimizing.

## Step 1 - reproduce and profile the load path

- Reproduce: load the full en/pt store the `explore` notebook used
  (`LexiconStore.from_data_fol(<full corpus>)`), outside the notebook so timing is
  clean.
- Instrument with `cProfile` + a coarse per-stage `perf_counter` split of
  `from_data_fol`: (a) codec `_load_table` Parquet reads, (b) SQLite DB build /
  index creation, (c) any eager work at construction.
- Separately time the **query** calls the notebook actually made (`get_all_lemmas`,
  `get_all_concepts`, ...): is the cost in *building* the store or in a bulk
  `get_all_*` reconstructing every model through the codec? The 05.2 hypothesis is
  the latter - confirm or refute it with numbers.

## Step 2 - locate the discrepancy

Pin which of these dominates (do not guess - read the profile):

- per-row model reconstruction (`model_from_row` x N) on a full-table `SELECT`;
- repeated JSON-text decode of the nested list/dict columns;
- the senses per-language partition load;
- any accidental N+1 (e.g. hydration walking edges, or a query in a loop).

## Step 3 - decide the fix (smallest that works)

Candidate directions, to choose from the profile, not in advance:

- **Don't reconstruct everything for exploration.** Bulk/overview inspection
  should go through the DuckDB-over-Parquet `inspect_table` path (phase 4,
  inspect-only), reserving `LexiconStore` for point / bounded-adjacency queries -
  i.e. treat `get_all_concepts()` as a smell at full scale, not a fix target.
- **Cache the built SQLite.** If the SQLite build itself is the cost, persist the
  built DB file and reuse it across sessions instead of rebuilding on every
  `from_data_fol` (build once per corpus version; key on the `_build.json`
  manifest).
- **Lazy / streamed query results** if a bulk reconstruction is unavoidable.

## Step 4 - measure build + load memory (Observation 3)

- Peak RSS for (a) `build_initial` (the transform + write) and (b) the store load,
  measured **separately** (`/usr/bin/time -v`, `tracemalloc`, or `resource`).
- Compare against the phase-3 ~1.9 GB resident estimate; record the en/pt actuals.
- **Go/no-go on the per-language restructure**: 05.1 Bug D's "next memory ceiling"
  note flags writing per-language and not holding all five languages' models at
  once (ILI-keyed merge across per-language passes, or a two-pass build). The
  memory numbers here decide whether that restructure is required *before* the full
  five-language build or whether the box can take it as-is.
